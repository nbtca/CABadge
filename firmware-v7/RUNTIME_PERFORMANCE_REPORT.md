# CABadge 7.2.3：任务占用与实体屏 FPS 测试

2026-09-21，PCB c7c59dff，COM3。先采样 7.2.0 计时基线，再修正主循环等待和 FPS 自刷新误计；本报告记录实际读回数据。7.1.9 异步存储草稿已保存在 F:/CABadgeBuild/temp/async-draft-before-monitor，未混入本次发布。

## 结论

- 静态壁纸 main 从单核 97.31% 降至 4.51%。原因是 100 Hz FreeRTOS 下 `pdMS_TO_TICKS(5)` 等于 0；原循环持续忙轮询。现用已有 esp_timer 服务实现最低 5 ms 循环周期，长绘制周期不再额外等待。没有创建新的 GUI 定时任务。
- 旧 USB 像素投屏已在 7.1.5 移除，当前没有后台传图任务。本轮比较的是仍需保留的 USB 状态查询，不是重新开启旧投屏。
- 最终版 Carousel 正常 6.6 FPS；每秒 5 次 USB 状态查询时 6.5 FPS。没有证据表明这项查询是主要瓶颈；单轮差异不能解释成性能收益。
- 主要动画负载仍在 main 内的 LVGL 绘制与 LCD 提交。修复的是无用忙轮询，不能宣称画面帧率大幅提高；没有删除 Wi-Fi、BLE、HTTP、壁纸或 USB 服务。

## 测量口径

- CPU 是 FreeRTOS 任务运行时间差值除以采样墙钟时间：100% 为占满一个核心，两核合计 200%。IDLE 是空闲容量，不是需要删除的后台任务。任务栈水位为历史最小剩余字节，不代表瞬时栈占用；各任务共享堆，没有伪造“每进程独占堆内存”。
- UI FPS：有内容变化的 LVGL 渲染完成次数/秒。LCD FPS：对应刷新周期最后一块成功传完的次数/秒，局部刷新也计一次，不是把每个 DMA 分块计一帧，更不是全屏扫描 Hz。TE 未接，不能在软件中实测面板扫描刷新率或像素发光延迟。
- FPS 显示每秒更新，排除自身文字刷新；静态页面 0 为正常。LVGL 9.4 `get_max_row()` 在渲染中发送的 INVALIDATE_AREA 只是缓冲高度取整询问，已从内容变化计数中排除。
- 分组 work_wall_pct 包含抢占和等待，不能当作任务 CPU 比例；GUI 分组包含 LCD 等待。渲染均值由 RENDER_START/READY 墙钟扣除同步 flush 时间获得，传输均值是整个 flush 路径，含拷贝/排队/等待，不是纯线速。
- 基线每场景约 10 秒，最终每场景约 12 秒，每秒 USB 抽样一次；统计区间是首末样本之差。都启用正常动画。用户在前一轮更改了亮度等设置，各轮原值见 JSON；背光仍受同一物理上限限制，没有把异轮采样当严格实验室重复试验。
- 关闭 FPS 且电脑停止采样 5 秒后，帧/分组计时停用；FreeRTOS 任务运行时间统计仍由诊断构建启用，存在额外内存和上下文切换计时开销。

## 修复、验证与保留的问题

- `usb_screen/device/src/main.c`：真实 5 ms 最低轮询周期；复用原 USB 协议，增加诊断快照和自动对照场景；LCD 数据路径不变。
- `usb_screen/device/src/runtime_monitor.c/.h`：任务、堆、分组计时和内容 FPS 计数；设置关闭后停止常规帧/分组采样。
- `ui/badge_ui.c/.h`：设置→显示→FPS 开关、顶层小标签、息屏隐藏；默认关闭，不写 NVS。
- `usb_screen/device/src/CMakeLists.txt`、`sdkconfig.defaults`：接入监测模块/运行时间统计；`runtime_probe.py` 输出可复查 JSON/JSONL。
- `usb_screen/build.ps1`、`workbench.py`、`performance_probe.py`：版本、发布及采样兼容；`test_runtime_monitor.py`、`render_benchmark.c` 验证自刷新、多分块计数、失败/关闭路径及实际 UI 开关。
- 最终 ESP32 构建成功；10/10 原生 CTest、生产 FPS 计数自检、本地控制检查、采样协议检查、工作台固件校验及离线烟测通过。实际只写入应用分区 0x10000，esptool 哈希校验成功，USB 读回版本 7.2.3-monitor。
- 7.2.0/7.2.1/7.2.2 的静态 HUD 约 0.6～0.7 FPS 是计数缺陷，保留原始证据；7.2.3 同场景实测 0。7.2.1 每轮额外一 tick 和 7.2.2 每轮额外 5 ms 的方案影响部分动效，最终改为只补足短循环的 5 ms 预算。
- 16:32 的 menu_idle/member_idle 被用户触摸改变页面；用户明确确认当时正在触摸，不判触摸漂移。本轮重测两项均 0 FPS，旧行不纳入静态比较。
- 本轮无线扫描请求成功、最终错误码 0，BLE 广播正常。没有重新测试手机 BLE 连接/GATT、Wi-Fi 连接吞吐或壁纸上传，不能用初始化正常替代完整功能回归。
- 仍需实物目视确认 FPS 开关和长时间稳定性；复杂 Carousel 图层调整/缩放仍是后续绘制热点。设置保存和文件提交的最坏延迟未在本轮重写或覆盖。
