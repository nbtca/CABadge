# 7.3.4-async 双绘图缓冲实板对照

2026-09-21，基于用户指定的 7.3.3-fluid、PCB c7c59dff。已编译、烧录并通过协议读回版本。用户本次目视反馈：**“显示正常，没有发现撕裂或重复”**。工作台默认安装更新到此版；8.0 Article 源码及发布包保持独立。

## 已实现

- 两块 360×360 RGB565 PSRAM 绘图缓冲，合计 518,400 B。仍为 LVGL PARTIAL 模式：容量足够容纳全屏，但局部变化继续按脏矩形输出，没有改成每次强制全屏。
- GUI 在 core0；新增 `badge_lcd` 任务在 core1、优先级3、栈3072 B，执行原有 QSPI DMA 驱动。LVGL 可以在另一块绘图缓冲上继续绘制。
- 同时只允许一个在途刷新区域。队列复制区域坐标并保留像素缓冲所有权，上一笔完成前不提交下一笔；GUI 通过 `flush_wait` 或非阻塞 `flush_poll` 收取完成结果，再通知 LVGL。后台任务不调用 LVGL、不更新 UI 对象。
- 保留 40 MHz QSPI、两个内部32行 DMA 暂存块、同一区域连续 CS 的传输方式。DMA 事务全部回收后才复用缓冲，包括失败路径。没有改成每画十行就把未完成的一帧逐条写屏。
- 内部显示状态改为原子变量；背光更新归 GUI，避免 worker 与 GUI 同时更新背光。
- 依据此前主任务栈高水位，主任务栈从16384减至12288 B，为新增3072 B显示任务及队列留空间。没有削减无线缓冲。
- FPS统计保存提交时的内容标记，旧帧完成不会被新帧/HUD状态误归类；渲染计时仅减去 GUI 实际等待，不减去与绘制重叠的全部 DMA 墙钟时间。

## 实板结果

同轮基线：[7.3.3 JSON](../outputs/performance/runtime-20260921-205348.json)；新版首轮：[7.3.4 JSON](../outputs/performance/runtime-20260921-210103.json)。每场景约8秒，首末采样有效窗口约7秒；不是三轮中位数。两版 BLE 广播开启，Wi-Fi 开启但未连接。新版未连接状态曾报告 error=-1，扫描结束 error=0。

|场景|7.3.3|7.3.4|变化|
|---|---:|---:|---:|
|壁纸浏览|26.31 FPS|26.74 FPS|+1.6%，变化小|
|上下抽屉|17.95 FPS|19.29 FPS|+7.5%|
|蓝色名片切换|16.91 FPS|21.26 FPS|+25.7%|
|壁纸 + USB状态5Hz|26.34 FPS|27.45 FPS|+4.2%|
|壁纸 + Wi-Fi扫描|26.46 FPS|27.16 FPS|+2.6%|
|壁纸 + BLE扫描|25.92 FPS|27.83 FPS|+7.4%|
|壁纸 + FPS显示|26.44 FPS|26.73 FPS|+1.1%|
|静态页面 / HUD静态 / 息屏|0|0|无新增内容刷新|

这是内容刷新周期最终传输完成率，包含动画间歇，不是 LCD 面板扫描 Hz，也不是无撕裂完整视觉帧的仪器测量。

|场景|旧/新平均渲染耗时 ms|旧/新平均传输任务耗时 ms|
|---|---:|---:|
|壁纸浏览|17.69 / 18.15|5.55 / 7.57|
|上下抽屉|20.42 / 21.82|7.50 / 9.88|
|名片切换|24.30 / 26.26|13.97 / 17.21|

**两个耗时不能在新版相加估算帧率，因为它们重叠。**单项耗时没有下降，但名片整体提交率提升，符合流水线重叠的效果。跨核 PSRAM/缓存访问竞争和调度是耗时增加的可能原因，尚未做硬件总线追踪，不能认定唯一原因；不宣称双缓冲翻倍或达到60 FPS。

新版 `main` 动画单核CPU约81%～87%，`badge_lcd` 约16%～30%；新增传输任务确实被调度。任务CPU占用不是纯绘图CPU时间。

|内存项|基线|新版首轮|
|---|---:|---:|
|周期采样内部空闲最低|8,127 B|9,027 B|
|内部最大连续空闲块最低|4,608 B|4,608 B|
|PSRAM空闲最低|6,844,024 B|6,581,876 B|
|主任务剩余栈高水位|约9 KiB级|5,168 B|
|新增显示任务剩余栈高水位|无此任务|2,060 B|

PSRAM占用增加262148 B，接近新增一块259200 B绘图缓冲和分配开销。内部空闲没有因新增任务下降，但最大连续块仍小，不能由本轮短测保证连接/上传高峰和长期碎片安全。

## 专项采样与干扰记录

[逐帧专项结果](../outputs/performance/20260921-210335-859618.json)覆盖六场景、字节数、SPI队列/线传输/等待及堆统计。为延续既有逐帧探针，详细模式在每次 RENDER_READY 等待最后一笔传输，并标记 `timing_mode=async_frame_fence`。**这个模式关闭跨帧重叠，不能用它替代上表常态运行的性能结论。**其名片约17.4 FPS与常态约21.3 FPS的差异不能隐去。队列统计指SPI事务排队，不包含worker作业在调度前的全部等待。

第二轮 `runtime-20260921-210405.json/.jsonl` 的静态场景出现不同页面编号。用户随后明确说明“我刚刚在摸”，因此保留整轮数据但排除正式A/B对照；不将它判为后台重绘故障。自动采样已结束。

## 显示验收与剩余限制

用户在本版烧录、自动测试结束后，对左右切名片/上下拉面板的提问反馈“显示正常，没有发现撕裂或重复”，记为本轮目视复测通过。没有提供精确测试时长、高速录像或TE波形，不能扩大为所有场景绝对零撕裂。

TE未接。双绘图缓冲保证主控侧正在传输的像素不会被LVGL提前覆盖，连续CS减少块间空隙；屏幕内部扫描仍未与写GRAM硬件同步。保留旧版回退包，后续若出现断层需记录触发场景。

本轮未用模拟器验收。代码检查包括 `test_display_worker.py`、`test_async_flush.py`、`test_physical_display.py`、`test_runtime_monitor.py` 和采样工具自检；覆盖延迟DMA期间另一缓冲可绘制、坐标复制、错误回传、完成通知不提前/不重复、跨帧归属和源数据生命周期。编译/烧录日志及源哈希在发布包保存。

未做：新版手机BLE连接/GATT、Wi-Fi连接/上传并发、长时间内存稳定性、手指接触到像素发光的仪器延迟测量。服务代码未重构不等于已完整复测。此次没有改变7.3.3的UI页面、手势或壁纸存储协议。

## 修改文件与交付

- `usb_screen/device/src/main.c`：双绘图缓冲、异步提交/完成、探针计时。
- `display_worker.c/.h`：复用现有Article worker基本结构，改为core1并增加非阻塞完成读取；未引入其其他页面/服务。
- `physical_display.c`：跨任务显示状态原子化及背光归属；像素发送顺序/时钟不变。
- `runtime_monitor.c/.h`：异步完成与GUI实际等待分开统计。
- `sdkconfig.defaults`、设备 `src/CMakeLists.txt`：主任务栈和新增worker构建。
- `ui/badge_ui.h`、`usb_screen/build.ps1`、`runtime_probe.py`、`performance_probe.py`、`workbench.py`：版本、独立发布、计时说明、默认安装入口。
- 四个上述生产代码检查文件：新增/调整验证。

发布目录 `outputs/cabadge-v7-async-20260921`；源码与旧基线快照、二进制及日志均在F盘。发布时 `verification.json` 的 PENDING 原义保留，烧录后/用户反馈在 `hardware-verification.json`。根目录主测试记录使用 R35，避免与另一对话 Article R34 的编号冲突；两条分支的显示结论不混用。
